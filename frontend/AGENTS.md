# Frontend instructions

## Область действия

Правила относятся ко всему каталогу `frontend/`: исходному коду, тестам, конфигурации и npm-командам. Архитектурные правила для страниц, фич, auth и API относятся прежде всего к `frontend/src`.

Все npm-команды выполняй из `frontend/`. При запуске из корня используй `npm --prefix frontend run <script>` или сначала перейди в каталог.

Перед изменениями изучи относящиеся к задаче файлы, текущий diff и реальный backend-контракт. Изменяй только необходимое. Не выполняй несвязанный рефакторинг, массовое переименование, форматирование соседнего кода или исправление посторонних ошибок.

Не изменяй backend, auth-инфраструктуру, общий API-клиент или proxy молча. Если это действительно требуется задачей, объясни причину и границу изменений.

Frontend-правила не применяй автоматически к backend, инфраструктуре и CI/CD.

## Текущее состояние

Frontend является минимальным auth-aware UI-приложением с предметными страницами главной и библиотеки.

Уже существуют:

* общий `apiFetch` и `ApiError`;
* cookie-only auth-инфраструктура;
* `AuthProvider` и `useAuth()`;
* `AppRouter`, `RouteGuard` и конфигурация маршрутов;
* защищённая главная страница с данными из `GET /bff/home` и feature-слоем `src/features/home`.
* защищённая библиотека с cursor-пагинацией из `GET /bff/library/decks` и `GET /bff/library/cards`, а также feature-слоем `src/features/library`.
* защищённый каталог публичных колод на `/catalog` из `GET /bff/catalog` и feature-слоем `src/features/catalog`;
* защищённая практика на `/practice`: настройка новой сессии по `?deck=...`, восстановление по `?session=...`, список тренировочных сессий и feature-слой `src/features/practice`;
* защищённая история карточек тренировочной сессии на `/practice/sessions/:session_uuid/history`.

Сейчас зарегистрированы guest-маршрут `/login`, protected-маршруты `/`, `/library`, `/library/:deck_uuid/edit`, `/catalog`, `/practice`, `/practice/sessions/:session_uuid/history` и `/settings`, а также публичный wildcard-маршрут `*` со страницей 404. Их route-pages расположены в `src/pages/LoginPage`, `src/pages/HomePage`, `src/pages/LibraryPage`, `src/pages/LibraryDeckEditPage`, `src/pages/CatalogPage`, `src/pages/PracticePage`, `src/pages/SessionHistoryPage`, `src/pages/SettingsPage` и `src/pages/NotFoundPage`. Остальных маршрутов и страниц пока нет.

Не считай страницу, маршрут или фичу существующими только потому, что путь встречается в redirect, константе или примере. Источники истины — текущее дерево, `route-config.ts`, backend-код и OpenAPI.

Если задача создаёт первую страницу, маршрут или фичу, обнови этот раздел в той же задаче.

Не используй `dist/` как источник архитектуры: это сгенерированный и потенциально устаревший артефакт.

## Auth

`AuthProvider` расположен над router. В страницах и компонентах используй auth только через:

```ts
import { useAuth } from "../../auth/hooks/useAuth";
```

Корректируй относительный путь импорта для текущего файла.

Consumer API содержит `status`, `user`, `error`, `isAuthenticated`, `login()`, `logout()` и `refresh()`. Контекст также содержит `initialize()`, но это provider/router-level операция; обычные страницы и feature hooks не должны её вызывать.

Не создавай:

* вторую auth-систему или локальную копию текущего пользователя;
* хранение access- или refresh-токенов в JavaScript-хранилищах или React state;
* чтение или декодирование JWT;
* ручной `Authorization` header;
* прямые вызовы `/auth/refresh` или `/users/me` из страниц;
* собственный refresh interceptor, route guard, logout или auth redirect;
* прямое использование `AuthContext` вместо `useAuth()`.

Фактический поток:

* запуск: `GET /users/me`;
* login: `POST /auth/login`, затем `GET /users/me`;
* logout: локальное завершение сессии, затем `POST /auth/logout`;
* обычный auth-enabled запрос после `401`: refresh и не более одного повтора исходного запроса.

Автоматический refresh не выполняется, если запрос передан с `auth: false` или `retryOnUnauthorized: false`.

Одновременные refresh-запросы объединяются внутри одного экземпляра `ApiClient`, обычно в пределах одной вкладки. Между вкладками auth-мутации могут сериализоваться через Web Locks, но не объединяются в один HTTP-запрос.

События входа и выхода синхронизируются через `BroadcastChannel`, когда он доступен. Не обещай межвкладочную синхронизацию в окружении без него.

Неудачный refresh не всегда означает `unauthorized`:

* `401` или `403` переводят auth-состояние в `unauthorized`;
* сеть, contract error, `5xx` и другие ошибки могут перевести его в `error`;
* повторный `401` завершает сессию.

`auth.refresh()` предназначен для явной повторной синхронизации сессии. Не вызывай его в обычной странице или feature hook без конкретной необходимости.

Frontend не читает токены из ответа. `HttpOnly`, `Secure`, `SameSite`, сроки жизни cookies и отсутствие токенов в response body подтверждай по backend-коду и OpenAPI при auth-задачах.

Не изменяй `AuthProvider`, `AuthContext`, `RouteGuard`, refresh, cookies или межвкладочную синхронизацию, если задача прямо не касается этой инфраструктуры.

## Маршруты и страницы

Все корневые маршруты регистрируй только в `src/app/router/route-config.ts`. Используй существующие уровни доступа: `public`, `guest`, `protected`.

Не создавай дополнительный `BrowserRouter`, корневой `Routes`, route guard или ручную проверку auth внутри страницы.

`RouteGuard` использует `/login` как guest entry и защищённый пустой маршрут `/` как authenticated fallback. Неизвестные URL обрабатывает публичный wildcard-маршрут со страницей 404. Перед добавлением нового `guest` или `protected` маршрута проверь, что необходимые цели действительно зарегистрированы. Если их нет и задача не включает auth-страницы, не придумывай их молча — сообщи об ограничении.

Route-page, загружаемую через `React.lazy`, размещай в отдельной папке:

```text
src/pages/DecksPage/
  DecksPage.tsx
  DecksPage.module.css
  index.ts
```

Route-page должна иметь `default export`. Локальные стили размещай рядом в CSS Module, если странице действительно нужны локальные стили. Не создавай пустые CSS-файлы, hooks, компоненты или feature-слои только ради шаблона.

Страница должна преимущественно собирать UI и вызывать предметную логику. Выноси код, когда он имеет самостоятельную ответственность, повторно используется или содержит нетривиальное состояние. Не дроби простой JSX только ради уменьшения файла.

## API и backend-контракт

Запросы к backend приложения выполняй через:

```ts
import { apiFetch } from "../../api";
```

Обычный `fetch` используй только для внешнего сервиса или неподдерживаемого транспортного сценария и объясни это в итоговом сообщении.

В `apiFetch` передавай backend-path без frontend base URL:

```ts
apiFetch("/decks/");
```

Не передавай `/api/decks/`. Завершающий `/` должен в точности соответствовать реальному backend-маршруту.

`VITE_API_URL` используется как base URL; `/api` является только значением по умолчанию.

Vite proxy:

* работает только в dev server;
* включается только при заданном `VITE_PROXY_TARGET`;
* обрабатывает запросы `/api/*`;
* удаляет `/api` перед отправкой в backend.

Абсолютный `VITE_API_URL` обходит dev proxy. Не полагайся на Vite proxy как на production-маршрутизацию.

`apiFetch` по умолчанию использует `credentials: "include"`, но caller технически может это переопределить. Не меняй `credentials` для запросов к backend приложения без конкретной причины.

Перед использованием endpoint проверь:

* HTTP-метод, точный URL и trailing slash;
* query-параметры и request body;
* response schema и коды ошибок;
* авторизацию и права;
* тип идентификатора;
* пагинацию.

Приоритет источников:

1. backend route и schema;
2. сгенерированная OpenAPI как перекрёстная проверка;
3. backend-тесты;
4. актуальная документация;
5. существующий frontend-код.

Старый frontend-вызов не является доказательством контракта. При противоречии источников не угадывай — сообщи о нём.

Не придумывай endpoint, поле или операцию и не подменяй отсутствующий backend mock-данными без прямого указания пользователя.

Предметные запросы размещай в API-модуле соответствующей фичи, когда такая фича действительно существует. Не добавляй предметные endpoints в общий `api-client.ts` и не создавай пустой feature-слой заранее.

Предпочтительный поток для нетривиальной фичи:

```text
Page -> feature hook/model -> feature API -> apiFetch -> backend
```

## Ошибки и асинхронность

Проверяй API-ошибки через `isApiError` и различай `status`, `code`, `message`, `details`.

Учитывай:

* `status === 0` может означать сеть, отмену или client/contract error; различай их по `code`;
* финальный `401` обычного auth-enabled запроса уже прошёл refresh и повтор;
* auth endpoints и явно отключённый retry являются исключениями;
* `403` обычной feature-операции означает отсутствие доступа, а внутри auth-потока — потерю авторизации;
* ожидаемая отмена не должна показываться как сетевая ошибка;
* технические детали backend не должны без необходимости попадать в UI.

Не запускай refresh, logout или redirect повторно на уровне страницы после финального `401`.

Для загрузки данных учитывай размонтирование и устаревшие ответы. Используй `AbortController`, когда это подходит. Отмена ожидания на клиенте не гарантирует, что уже отправленная backend-мутация была отменена или откатилась.

Обрабатывай только применимые состояния: загрузку, пустой результат, успех, ошибку, отсутствие доступа и состояние мутации. Не создавай искусственные состояния для синхронного компонента.

## TypeScript и структура UI

Соблюдай текущие строгие настройки:

* `verbatimModuleSyntax`: типы импортируй через `import type`;
* `noUnusedLocals` и `noUnusedParameters`: не оставляй placeholder-код;
* `erasableSyntaxOnly`: не используй обычные `enum`, runtime `namespace` и parameter properties;
* не используй `any` и необоснованные type assertions;
* не скрывай расхождение backend-контракта ослаблением типов;
* различай optional и nullable поля.

Следуй существующим ESLint и Prettier-конфигурациям. Не добавляй зависимость, новый router, дублирующий API-клиент или глобальный state manager без необходимости.

## Проверки

После изменений запускай применимые команды из `frontend/`:

```bash
npm run format:check
npm run typecheck
npm run lint
npm run test
npm run build
```

Во время разработки можно сначала запускать целевые тесты.

Добавляй или обновляй тесты при изменении поведения, API/model-логики, auth или маршрутизации. Текущий Vitest использует `node` environment; не предполагай наличие DOM или React Testing Library и не добавляй новый test stack без необходимости.

Не утверждай, что проверка прошла, если она не запускалась. Если команда невыполнима или падает из-за существующей несвязанной ошибки, укажи команду, причину и связь с текущей задачей.

## Критерий завершения

Для любой задачи требуется:

* выполнить запрошенное изменение без несвязанного расширения scope;
* соблюдать существующую архитектуру и подтверждённый backend-контракт;
* не дублировать общие auth, router и API-механизмы;
* выполнить доступные проверки;
* честно сообщить о невыполненных проверках и ограничениях.

Дополнительно, только если применимо:

* если добавлен маршрут — зарегистрировать его в `route-config.ts`;
* если route-page загружается через `React.lazy` — предоставить `default export`;
* если добавлены предметные запросы — типизировать их и разместить в соответствующей фиче;
* если есть асинхронное состояние — обработать отмену, устаревшие ответы и применимые UI-состояния;
* если изменилось поведение — добавить или обновить тесты.

Отсутствие маршрута, API-вызова, feature hook или асинхронного состояния не делает задачу незавершённой, если они не нужны для выполнения запроса.
