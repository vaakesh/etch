# Правила логирования интеграционных тестов

Применять к тестам, фикстурам и вспомогательным функциям в `backend/tests/integration/`, включая `conftest.py`.

## Уровни и способ записи

- Использовать стандартный `logging` и логгер модуля: `logger = logging.getLogger(__name__)`.
- Штатные действия тестов и фикстур логировать на `debug`: подготовку ресурсов, проверку конфигурации, настройку зависимостей и очистку. Не использовать для них `info`.
- `warning`, `error` и `exception` оставлять для реальных нештатных ситуаций, если сообщение добавляет полезный контекст. Ожидаемая ошибка в негативном тесте сама по себе не требует такого лога.
- Значения передавать аргументами логгера через `%s`, а не подставлять заранее через f-строки, `.format()` или конкатенацию.

## Текст сообщений

- Писать сообщения на английском, весь статический текст — строчными буквами, включая названия и сокращения: `redis`, `database`, `app`.
- Значения переменных выводить как есть. Не применять `.lower()` к данным или готовому сообщению ради соблюдения регистра.
- Формулировать кратко и конкретно: действие и ресурс, при необходимости — этап или полезное значение. По сообщению должно быть понятно, что происходит.
- Не использовать многоточия, восклицательные знаки, декоративные разделители и многословные обороты вроде `was successfully created`.
- Для одинаковых действий использовать одинаковые формулировки. Различать очистку до и после теста через `before test` и `after test`.
- Различать начало и завершение операции: `creating database engine` писать перед созданием, а `async database session factory created` — только после успешного создания.

## Где нужны логи

- Логировать значимые этапы, которые помогают найти причину сбоя: создание и освобождение общих ресурсов, проверку тестовой базы, настройку и очистку dependency overrides, очистку базы и Redis до и после теста.
- Обычно достаточно одного сообщения на этап. Не добавлять пару «начало / успех» для каждого простого действия; оба сообщения нужны только если завершение даёт отдельную диагностическую пользу.
- Не дублировать одно событие в фикстуре и вызываемой ею вспомогательной функции. Например, очистку логировать в `clean_database` с указанием этапа теста, без повторного сообщения в `truncate_database`.
- Не логировать каждое присваивание, подготовку аргументов, запрос или `assert` без диагностической необходимости. Не добавлять логи только ради того, чтобы они были в каждой функции.
- Не дублировать отчёт pytest о прохождении теста или traceback исключения без дополнительного контекста. Не менять обработку исключений и поведение фикстур ради логирования.

## Примеры

```python
logger.debug("test database verified: %s", settings.db_name)
logger.debug("creating database engine")
logger.debug("disposing database engine")
logger.debug("clearing database before test")
logger.debug("clearing database after test")
logger.debug("clearing redis database before test")
logger.debug("test app dependency overrides configured")
logger.debug("clearing test app dependency overrides")
```

Перед завершением правок проверить уровни, нижний регистр статического текста, отсутствие дублей и соответствие формулировки месту вызова.
