# Правила интеграционных тестов

Применять к `backend/tests/integration/`. Логирование — по [logging_rules.md](logging_rules.md).

Если при написании тестов не получается соблюсти эти правила, остановить написание, объяснить пользователю затруднение и задать вопрос. Продолжать только после решения пользователя.

## Структура

- Файл — `test_<domain>_<action>.py`, класс — `Test<Action>`, метод — `test_<scenario>_<expected_result>`.
- Один тест — один логический сценарий. Разделять подготовку, действие и проверки пустыми строками.
- Однотипные варианты оформлять через `pytest.mark.parametrize` с понятными `id`. Объединять существующие тесты параметризацией, только если сохраняется один и тот же логический сценарий и смысл проверок. Успех и ошибки проверять отдельно.
- Всегда проверять новый и соседний тестовый код на повторения. Общую подготовку выносить в фикстуры, повторяющиеся действия — во вспомогательные функции, если это упрощает код и сохраняет явными значимые данные и проверки сценария.
- Сохранять стиль существующего файла. Аннотировать используемые фикстуры и параметры.
- Для асинхронных тестов использовать принятый в проекте scope: `pytestmark = pytest.mark.asyncio(loop_scope="session")`.

## Подготовка

- Использовать общие фикстуры и фабрики: `user_factory`, `auth_client_factory`, `client_factory`, `async_session_maker`.
- Авторизовывать клиента реальным входом через фабрику. Для разных пользователей и сессий создавать отдельных клиентов.
- Проверять связку HTTP → сервис → БД/Redis. Не мокать внутренние сервисы и репозитории; внешние сторонние системы подменять на границе.
- Использовать только тестовую инфраструктуру и существующую очистку БД/Redis. Тесты должны быть независимы от порядка запуска.
- Данные задавать явно и детерминированно. Значимые для сценария поля оставлять видимыми в тесте.

## Проверки

- Всегда проверять HTTP-статус и полный значимый контракт ответа. Ожидаемые значения задавать явно, не вычислять через тестируемые схемы или функции.
- Динамические UUID и даты проверять отдельно: формат, связь с созданной сущностью и совпадение с БД. После этого сравнивать остальную структуру целиком.
- После записи читать БД через новую сессию: проверять сохранённые значения, принадлежность записи и сохранность полей, которые запрос не меняет.
- Для ошибочного запроса проверять код и структуру ошибки, а также отсутствие записи или частичного изменения данных.
- Нестабильные внутренние детали библиотек, например адрес функции в пути ошибки, не фиксировать строкой. Проверять стабильное расположение поля и содержимое ошибки.
- Не подгонять ожидания под обнаруженный баг. Если исправление приложения вне задачи — сообщить о нём.

## Сценарии

- По применимости: полное и частичное обновление, нормализация, границы, пустое тело, `null`, неверные значения, конфликты, отсутствие авторизации и прав.
- Для обновлений учитывать собственные неизменённые значения, изоляцию пользователей и видимость изменений после прогрева кеша.
- При смешанном запросе с валидным и невалидным полями проверять отсутствие частичной записи.
- Не переносить всю матрицу unit-валидации в интеграционные тесты: выбирать случаи, проверяющие взаимодействие слоёв.
- Проверять публичное поведение. Не добавлять циклы, сложную логику, проверки внутренних вызовов и лишние вспомогательные функции.

## Запуск

- Запускать изменённый файл через `uv run pytest` из `backend` в настроенном тестовом окружении; в контейнере также использовать `uv`.
- После успешной проверки расширять запуск только при риске для других сценариев. В результате указать, что запущено, число прошедших тестов или причину невозможности запуска.
