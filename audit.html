Итоговая оценка

Архитектура проекта понятна и уже имеет хорошие базовые решения: слои API/service/repository, транзакционный Unit of Work, refresh-ротация, ограничения данных и развитый кэш. Главный риск сейчас находится на стыке жизненного цикла колоды, архива и истории обучения. Там есть сценарии потери истории, раскрытия отозванного контента и невозможности завершить тренировку. Второй крупный блок — неполная согласованность Redis-кэша с PostgreSQL.

P1 — критичные ошибки

P1 · высокая уверенность

Пагинация библиотеки падает на неизученных колодах

UserDeck.last_studied_at допускает NULL, и SQL-запрос умеет сортировать такие записи. Но модель курсора требует обязательную дату, а кодек вызывает isoformat(). Если следующая страница заканчивается неизученной колодой, API формирует курсор из None и отвечает ошибкой вместо страницы.

Сценарий: две новые колоды → GET /bff/library/decks?limit=1 → ошибка валидации при создании next_cursor.

Исправление: сделать поле курсора nullable, явно кодировать null, проверить страницы «только NULL» и переход от изученных к неизученным.

Код: decks/models.py:233, decks/schemas.py:152, decks/service.py:424–433, decks/cursor.py:58–66. Воспроизведено вызовом реального метода сервиса с изолированным репозиторием.
P1 · приватность

Отзыв публикации оставляет публичную копию колоды

Перевод публичной колоды в приватную и её удаление всегда создают копию с is_public=True, даже если колоду никто не сохранял. Каталог выбирает все публичные колоды и не отличает архив. Владелец ожидает скрытия или удаления, но содержимое остаётся доступным всем, а повторные переключения создают новые копии.

Исправление: ввести отдельную архивную сущность или признак архива; выдавать снимок только пользователям, которые ранее сохранили колоду; не создавать архив при отсутствии потребителей.

Код: decks/service.py:112–181, 543–578, decks/repository.py:206–240. Подтверждено: update_deck(is_public=False) при нуле сохранений создал публичную копию.
P1 · доступ

Архивы принадлежат обычному аккаунту с жёстким ID 1

ARCHIVE_USER_ID = 1 применяется к копиям колод и карточек. В миграциях нет защищённого системного пользователя. На новой установке ID 1 может получить первый обычный пользователь и стать владельцем архивов чужого контента: штатные проверки владельца разрешат ему редактирование и удаление. Если пользователя 1 нет, внешний ключ сорвёт архивирование, а часть путей маскирует IntegrityError как конфликт имени колоды.

Исправление: убрать владение архивом из обычной модели пользователя или создать миграцией отдельного неаутентифицируемого системного субъекта с явным типом и запретом CRUD.

Код: decks/service.py:52, 126–147, 543–552. Условие эксплуатации зависит от содержимого реальной БД; механизм подтверждён по коду.
P1 · целостность данных

Архивирование ломает активную тренировку и удаляет историю

При отзыве публикации сохранённый UserDeck переносится на архив, но TrainingSession.deck_id остаётся на оригинале. Последний ответ ищет UserDeck по старому ID и откатывается с USER_DECK_NOT_FOUND. При удалении оригинала внешний ключ ON DELETE CASCADE уничтожает сессии и ответы чужого пользователя, хотя агрегированные счётчики у архивного UserDeck сохраняются.

Следствие: пользователь может потерять историю, streak и время обучения из-за действия автора колоды; статистика разных экранов расходится.

Исправление: отделить историю от жизненного цикла исходной колоды: хранить snapshot метаданных и nullable/soft-delete ссылку либо атомарно переносить все активные и исторические связи на архив.

Код: decks/repository.py:559–578, training_sessions/models.py:72–76, 211–215, training_sessions/service.py:89–107, 570–584. Финальный submit воспроизведён: ошибка, commit не выполнен.

P2

Неверный JOIN ломает выбор пользователей для очистки кэша

Запрос соединяет UserDeck по условию UserDeck.user_id == UserDeck.deck_id, не связывая таблицу users. Обычно он вернёт пустой список; при случайном совпадении ID может вернуть всех пользователей. Это означает пропущенную или массовую лишнюю инвалидацию при удалении аккаунта.

Исправление: выбрать distinct UserDeck.user_id с фильтром deck_id IN (...) или соединять User.id == UserDeck.user_id.

Код: decks/repository.py:851–865, вызов: users/service.py:388–418.
P2 · данные

Удаление пользователя завышает число сохранений чужих колод

Записи UserDeck удаляются каскадом, но Deck.saves_count у чужих колод не уменьшается. Каталог и суммарная популярность профиля остаются неверными.

Исправление: до удаления получить сохранённые чужие колоды, заблокировать их в стабильном порядке, пересчитать/уменьшить агрегаты и инвалидировать кэш. Полезен периодический invariant-check: counter равен числу is_saved.

Код: users/service.py:368–418, decks/models.py:217–227, изменение счётчика только в decks/service.py:1100, 1183.
P2 · auth

Смена пароля и logout не отзывают access JWT

Операция отзывает refresh-сессии, но access token проверяется только по подписи и сроку. Уже выданный JWT продолжает работать до exp, по умолчанию до 50 минут. Это ограничение текущей модели отзыва, особенно важное при компрометации токена.

Исправление: выбрать требуемую семантику: более короткий access TTL либо auth_version/session_id с надёжной проверкой при критичных запросах.

Код: auth/service.py:35–48, 208–238, auth/deps.py:54–73, config.py:16. Старый токен успешно декодирован после реального вызова change_password с временным тестовым ключом.
P2 · производительность

Argon2 выполняется синхронно внутри async-обработчиков

Хэширование и проверка пароля блокируют event loop worker-а. Локальный замер — около 58 мс для одного вызова; это не нагрузочный benchmark, но подтверждает сам механизм блокировки. При одновременных login/registration/change-password задерживаются и независимые запросы.

Исправление: вынести Argon2 в ограниченный thread pool, ограничить параллелизм по CPU/RAM и измерить p95/p99 при смешанной нагрузке.

Код: auth/utils.py:7–12, вызовы: auth/service.py:103–111, 223–231.
P2 · конфигурация

Пароли БД и Redis с особыми символами ломают URL

DSN собирается строковой интерполяцией без URL-encoding. Синтетический пароль test@host разобрался SQLAlchemy как другой host; Redis-пароли с # или / также ломают парсинг. Это создаёт неочевидные отказы при нормальной ротации секретов.

Исправление: создавать SQLAlchemy URL.create(...); для Redis использовать структурированный URL/quoted credentials. Добавить тесты на @:/#%[].

Код: config.py:45–49. Подтверждено локальным парсингом сформированных URL без сетевого подключения.
P2 · API-контракт

Допустимый username может не иметь доступного URL профиля

Регулярное выражение ^\S+$ разрешает символ /, но профиль адресуется одним path-сегментом. Имя abc/def проходит Pydantic, а /users/profile/abc%2Fdef даёт 404 после декодирования маршрута.

Исправление: ограничить username URL-safe алфавитом и зарезервированными словами; канонический идентификатор профиля лучше строить по UUID, а username оставить изменяемым slug.

Код: common/types.py:55–63, users/router.py:68–80. Подтверждено ASGI-запросом.
P2 · сессии

Список авторизационных сессий не представляет устройства и растёт без границ

При login не записываются IP и user-agent; API отдаёт главным образом null и revoked_at. Каждая refresh-ротация создаёт новую строку, а чтение возвращает всю историю без пагинации, фильтра активных записей и retention. Нет идентификатора устройства, признака текущей сессии и точечного отзыва.

Исправление: отделить семейство устройства от ротаций токена, сохранять безопасные метаданные, добавить список активных устройств, отзыв, пагинацию и очистку истории.

Код: auth/service.py:136–153, 186–206, auth/repository.py:43–55.
P2 · обучение

Повторный resume теряет активное время

Событие resume без начисления предыдущего интервала заменяет tracker и timestamp. Повторный запрос, вторая вкладка или retry через 20 секунд обнуляют эти 20 секунд; старый tracker после этого отвергается.

Исправление: начислять допустимый предыдущий интервал перед takeover либо сделать повторный resume идемпотентным.

Код: training_sessions/service.py:68–87, 445–495. Воспроизведено с фиксированным временем: начислено 0 мс вместо 20 000 мс.
P2 · эксплуатация

Backfill времени не отличает legacy от корректного современного нуля

Скрипт выбирает все завершённые сессии с active_study_time_ms = 0. Современная сессия законно может иметь ноль, если клиент не отправлял activity или интервалы превышали порог. --apply заменит этот ноль оценкой по времени ответов.

Исправление: ограничить обработку датой/ID миграции или признаком версии telemetry; хранить measured и estimated отдельно.

Код: scripts/backfill_training_session_time.py:23–53, 164–189. Скрипт безопасно работает в dry-run по умолчанию — это плюс.
P2 · схема БД

Миграции не соответствуют ограничениям ORM-моделей

Полный offline-upgrade из семи Alembic-ревизий не создаёт ряд ограничений, объявленных в моделях: проверки username/email и пять проверок колоды, включая неотрицательные counters/version и запрет self-source. База, развёрнутая миграциями, слабее модели.

Исправление: отдельная миграция с preflight-поиском плохих данных, очисткой и последующим добавлением ограничений. В CI сравнивать metadata и схему временной PostgreSQL.

Отсутствуют: username_min_length, username_trimmed, email_trimmed, ck_deck_saves_count_ge_0, ck_deck_words_count_ge_0, ck_deck_version_ge_1, ck_deck_title_not_blank, ck_deck_source_not_self. Код: users/models.py:134–159, decks/models.py:120–144.
P2 · удаление аккаунта

Удаление пользователя обходит уже существующую политику архива

Удаление отдельной публичной колоды пытается сохранить копию для подписчиков, а удаление её владельца просто каскадно удаляет колоды и сохранения. В коде есть TODO и незаконченный helper; у него дополнительная ошибка — скопированные карточки связываются со старой колодой.

Исправление: сначала определить продуктовую политику, затем один общий транзакционный workflow удаления/отзыва. Не включать текущий helper без исправления связей и интеграционных тестов.

Код: users/service.py:318–418. Латентная ошибка helper-а сейчас не является достижимой runtime-ошибкой.

P3 — неточности и долги

P3

Параметр days работает только для 7

get_user_activity_for_last_days() всегда начинает с today−6, а затем генерирует запрошенное число дней. При days=1 возвращается дата шестидневной давности, при 30 — диапазон уйдёт в будущее. Текущий caller передаёт 7, поэтому дефект пока скрыт.

training_sessions/service.py:291–326.

Каталог имеет нестабильный порядок

Offset-пагинация сортирует только по saves_count DESC. При равных значениях порядок не определён, поэтому между страницами возможны повторы/пропуски. Добавить хотя бы Deck.id DESC; для растущего каталога перейти на курсор.

decks/repository.py:206–240.

У владельца создаётся UserDeck.is_saved=False; favourite требует is_saved=True, а сохранить собственную колоду запрещено. Если избранное должно работать со всей библиотекой, это продуктовая ошибка; иначе ограничение нужно явно отразить в UI/API.

decks/service.py:503–508, 1082, 1137.

Редактирование текста карточки и прямое удаление карточки не всегда увеличивают Deck.version. Сейчас last_seen_version почти не используется, но это сломает будущую синхронизацию и уведомления об обновлениях.

P3 · политика

Лимитер fail-open: ошибка Redis даёт None, которое разрешает запрос. Для обычного API это доступность, но login/registration/change-password при сбое остаются без защиты и одновременно запускают тяжёлый Argon2.

redis/service.py:81–131. Это условный риск, а не признак текущего сбоя Redis.

Любую завершённую сессию можно прочитать без проверки приватности колоды; ответ раскрывает UUID/название и результаты. Возможно, это задуманный sharing. Политику нужно сформулировать и закрепить тестом доступа.

training_sessions/service.py:110–123.
P3 · deploy

Production-контейнер запускается с reload

Dockerfile всегда стартует Uvicorn с --reload, а Compose публикует PostgreSQL и служебные UI наружу. Для локальной разработки это удобно; production-профиль должен иметь отдельную команду, health/readiness checks, зависимости readiness и закреплённые образы.

Dockerfile:19, docker-compose.yml:20–77.
P3 · контракт

Ошибки тела JSON имеют два формата

Некорректный JSON вроде { проходит через общий handler и получает стабильный VALIDATION_ERROR, а невалидный UTF-8 возвращает стандартный FastAPI {"detail": ...}. Если frontend полагается на code, контракт неполон.

Подтверждено ASGI-запросами к POST /users/create: 422 со стабильным code и 400 со стандартным detail.

Стабилизация данных и приватности

Исправить четыре P1 как один lifecycle: публикация → save → start session → отзыв публикации/удаление → завершение → история. Убрать обычного пользователя ID 1 из архива. Добавить миграции недостающих constraints и интеграционные тесты PostgreSQL.

Критерий готовности: ни действие автора, ни удаление аккаунта не меняют чужую историю и не раскрывают отозванный контент.

Согласованный кэш и зелёный CI

Централизовать invalidation matrix, закрыть cache-fill races версиями, исправить JOIN, запустить PostgreSQL и Redis в CI. Восстановить 480/480 unit-тестов и добавить небольшой набор сквозных сценариев вместо массового дублирования mock-тестов.

Критерий готовности: изменения видимости, имени, счётчиков и сортировки наблюдаются сразу и одинаково через прямой API и BFF.

Надёжная авторизация и эксплуатация

Вынести Argon2 из event loop, определить отзыв access token, построить модель устройств/сессий, обработать Redis degradation для auth, исправить DSN. Разделить dev/prod контейнеры; добавить health/readiness, структурированные метрики ошибок, cache hit ratio и latency.

Критерий готовности: предсказуемая деградация и измеримые SLO, а смена пароля соответствует заявленной политике безопасности.

Учебный продукт

После стабилизации добавить состояние знания на уровне карточки, интервальные повторения, персональную очередь «сегодня», повтор ошибок и прогноз следующего повторения. Текущие агрегаты колоды недостаточны для качественного spaced repetition.

Полезные метрики: retention D1/D7/D30, доля завершённых сессий, due cards completed, повторные ошибки, медианное активное время, качество интервалов.

Каталог и социальные функции

Зафиксировать авторство архивов, лицензию/право на отзыв публикации, стабильную cursor-pagination и ранжирование. Добавить версии колоды, уведомления сохранившим пользователям и явный выбор: продолжить старую версию или перейти на новую.

Микросервисы пока не нужны: модульный монолит с PostgreSQL и Redis проще довести до корректности и наблюдаемости.

Область и ограничения аудита

  • Просмотрен только backend: приложение, тесты, Alembic, скрипты, Docker/Compose и Redis-конфигурация. Frontend не анализировался.
  • Проверено текущее рабочее дерево с уже существовавшими незакоммиченными изменениями. Хэши файлов backend и git status после аудита совпали со снимком до аудита.
